# Browser scope and document ownership

This is the next M5 implementation contract, not a claim of implemented page access. The current browser route pairs an extension storage installation and exchanges status only. No content script, host permission, DOM read or browser effect is activated by pairing. Source work and static checks must not exercise browser APIs during the owner's gaming restriction.

## Selected installation lifetime

A durable pairing is a revocable credential, not the selected everyday browser. Native Settings must explicitly select one exact saved pairing/revision and its immutable application UUID/revision before ordinary browser task ingress can use it. Selection does not rebind any old task target and does not imply account/profile-path proof. A replacement selection invalidates old connection and document capabilities before publication. An unavailable/corrupt/ambiguous selected record stays unavailable; never choose the first installed browser or first saved credential.

The current Settings-owned five-minute pairing session is setup-only. A later selected-installation connection may survive hiding Settings, but its pending management approvals may not. Keep those lifetimes separate: pairing/permission management proof remains tied to visible Settings and its original native challenge, while an established task connection requires current Windows principal/session, exact selected pairing, native connection generation and current action authority. Lock, explicit disconnect, selected-installation change and credential/scope revocation synchronously withdraw native admission. Mic mute/deafen alone do not revoke accepted browser tasks.

Pause/Stop and every action-epoch transition synchronously invalidate native document/effect admission even if the selected transport remains connected for status. Each dispatched request binds that exact action epoch; late responses cannot reestablish it. The extension must withdraw its matching capabilities when it receives authenticated invalidation and before admitting another operation. A queued/committed effect remains subject to the existing observed/unknown reconciliation rule; transport connection is never equivalent to permission to act. Settings hide invalidates management proof independently of this selected task lifetime once that source path exists.

No connection authenticates itself by supplying the selected catalog UUID. Native code resolves that configuration and validates it independently. The running browser/application/profile/account association remains unproven until a supported native/browser observation establishes the exact requested context. Extension installation UUIDs and owner labels cannot substitute for that evidence.

## Two-sided origin scope

Each native scope proposal has a fresh immutable UUID/revision, selected pairing/revision, native session and connection generation, exact canonical HTTPS origin, explicit supported operation set and a fixed expiration. Origin strings reject credentials, controls, opaque/null origins, path/query/fragment and noncanonical spellings. The initial supported surface uses domain hosts and standard HTTPS port 443; unsupported custom ports/IP schemes require a separately specified contract. No wildcard origin/subdomain or `all_urls` grant is inferred from a task.

Native Settings displays the exact proposal. Browser host permission must then be requested by an explicit extension popup gesture for that exact host pattern (`https://host/*`). A native message or background callback is not that gesture. Chrome's host permission only allows an extension API call; it is not an Avesra operation grant. Likewise, native approval without the actual browser permission cannot activate a scope. Bind completion to the original proposal, selected installation, session and native generation after every awaited browser/native operation.

Permission grant results may arrive after disconnect or proposal expiry. Such a result must never activate a replacement proposal or recreate native scope. Report any browser-only permission left behind accurately and allow explicit removal; do not automatically remove a pre-existing independently granted permission as a speculative rollback. Native scope revocation invalidates pending commands/observations before any browser removal operation. `permissions.onRemoved` also invalidates the corresponding native scope and extension capabilities. Recheck actual `permissions.contains` immediately before each document operation instead of treating an earlier setup reply as permanent proof.

Persist native grants only after both current sides are established, with owner identity and immutable scope revision. Store operations remain bounded and retain their actual worker slot through completion. Uncertain publication is reconciled by reading exact saved state, not repeating approval or an external effect. No scope credential is delivered to page code, URLs, DOM, logs or model text.

Initial limits are one selected installation, at most 32 saved exact-origin scopes and one pending scope proposal with a fixed 45-second monotonic lifetime. Admission fails before mutation when a limit is reached. Chrome host-pattern matching can be broader than a full origin; `permissions.contains` is only evidence that Chrome permits the API call. The native canonical origin and supported-port policy remain separate exact checks at every ingress/effect boundary.

## Document reference

An extension-derived candidate identifies one tab, window and frame plus Chrome's document UUID. Native acceptance creates a separate opaque document capability bound to selected pairing/revision, current native session/generation, exact scope revision, canonical origin, active lifecycle and a monotonically advancing observation generation. Browser IDs are typed bounded integers; document IDs must be canonical non-nil UUIDs. Neither page content nor a model chooses native target IDs.

`frameId` persists across navigation. `documentId` changes on a new document but can survive cached/prerender/active transitions; it is not sufficient by itself. Before/after every async browser operation, validate current tab/window/frame/document ownership, actual exact origin, active lifecycle, permission and observation generation. `getFrame` uses exact documentId together with tab/frame identity. Pending navigation, `onBeforeNavigate`, `onCommitted`, history/fragment changes, tab replacement/removal, activation/focus changes relevant to the requested effect, permission removal and connection restart invalidate old observations. BFCache restoration cannot rely on DOMContentLoaded, which need not fire.

Use native/extension monotonic reception clocks for freshness. Chrome navigation event timestamps are internally comparable but may not agree with extension wall-clock time; do not compare them to `Date.now()` as proof of packet age. Responses repeat exact request UUID, native target revision, document capability, scope revision and observation generation. Unknown, duplicated, expired or replaced requests are discarded before publishing page data or dispatching effects.

Keep at most 16 live document candidates and one pending semantic request per selected connection; each observation/request has a fixed five-second budget including queue wait. Revisions advance with checked integer arithmetic; overflow invalidates the connection instead of wrapping or silently resetting identity. Navigation/permission/tab lifecycle handlers invalidate synchronously before starting async reconciliation. An operation snapshots its generation before `getFrame` and checks the same current generation after every await, so a late API result cannot hide an intervening navigation. A response does not refresh its observation's original lifetime.

## Semantic observation and effects

Inject only shipped fixed functions into the isolated world and exact requested document IDs. Never expose arbitrary code, caller-selected functions, raw selectors, CDP, cookies, network interception or a page-facing native message forwarding endpoint. A revoked or unregistered script may still exist in a document; every request must independently recheck current permission and ownership. A content script's presence is never authority.

Observation is bounded to at most 128 visible semantic nodes and the protocol's 64 KiB message cap, with separate per-node text limits. Exclude passwords, hidden/disabled fields, sensitive autocomplete fields and unsupported cross-origin frames. Element handles are opaque within the exact observation, generated by shipped extension code and retired on revision change. Roles/names/text/links are untrusted page data, not policy, identity or durable instructions. Account/project context is an explicit observed predicate with source evidence; a page title or guessed label cannot satisfy it.

Names/roles are capped at 256 UTF-8 bytes each, node text at 2,048 bytes, and aggregate extracted semantic text at 48 KiB before serialization. The complete serialized frame still must fit 64 KiB; no truncation may cut a UTF-8 sequence or silently claim omitted content was inspected. A truncated snapshot marks that fact and cannot establish a postcondition that depends on omitted nodes. These budgets constrain product operations, not a fixture/evaluation runner.

The native effect owner accepts only a durably claimed exact action tied to the selected scope/document target. Before the one effect, recheck current accepted task, grants/approval, session, document/element revision, user intervention and expected precondition. Fill preserves unrelated unsent content; submission requires explicit accepted submit scope and one dispatch identity. Unknown outcomes never trigger automatic input replay. Read-page workflows also preserve their actual UI side effects: opening a mail may mark it read and must not be represented as side-effect-free.

Page reading, navigation, fill and submit adapters remain implementation work. Pairing, scope selection or a semantic helper cannot be reported as completed Gmail, X or coding-app workflow. Login/MFA/CAPTCHA and unsupported contexts remain NeedsInput. No mailbox/account content or application interaction is used to qualify these paths during the current restriction.
