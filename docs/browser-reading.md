# Accepted browser reading

This M5 slice adds a typed, bounded semantic read behind the existing durable native action owner. The protected Settings document chooser remains metadata setup only. Pairing, Chrome permission, a saved scope, a page title and a model proposal are each insufficient to read page content. No browser API or page operation is exercised during source implementation.

## Authority and the durable owner

ReadPage must arrive as the exact Action revision already claimed by ExecutionController on the actual NativeEffects worker. The worker retains its exclusive ledger/input ownership until the actual bridge job settles, including after caller cancellation or a timeout. It does not open another Store, run a second dispatch owner, or reconstruct authority from history. An immutable native target UUID binds actor, selected installation revision, pairing revision, configured browser AppRecord/revision, exact Read scope/revision, strict origin and exact tab/window/frame/document identity. Native setup observations may supply candidate metadata to a later native accepted-target resolver; they are not durable grants or task admission. The currently absent qualified producer leaves this ingress dormant.

The Action target must equal that native document target; ReadPage.origin must equal its strict browser::Origin, not merely the broader generic HTTPS parser. Binding to the configured browser app remains owner configuration, not proof of the running browser executable/account/profile path. A driver requiring account/project identity must establish that separately or return NeedsInput. Target replacement gets a new UUID and does not rebind old accepted tasks.

Before publishing one read request, validate the original accepted actor/payload/grant, source device/session and frozen capture provenance, current action epoch/cancellation, selected authenticated browser session/generation, target, current owner principal, AppRecord and unrevoked scope. Keep native disk/OS reads outside Runtime.local and use the existing ledger worker for its own store/catalog checks, never a callback that queues behind that same worker. The final durable authorize callback runs after potentially blocking inspection and immediately before native bridge publication. For this read-only adapter the existing commit marker means disclosure admission, not an OS mutation. A lost result after admission is an unknown read outcome; no automatic replay.

The native bridge owns one request from before preparation through actual extension completion. Its fixed ten-second monotonic budget is also capped by the original accepted action lifetime. Native→extension serialization only reduces remaining time; status polling, reconnect and revalidation never renew it. Session/action/scope/target withdrawal immediately closes publication without waiting behind SQL or Chrome APIs. Browser requests bind dispatch, action revision, task, actor, exact target revision and native browser context. These are correlation fields on the wire, never authority supplied by the extension. Native results are applied only to the original claimed dispatch.

## Versioned request and observation

The integrated route must advance browser protocol, authentication and comparison transcript together to v6. Existing v5 peers fail negotiation; pairing storage stays schema1 and pipe framing stays v1. A new required nullable read request in status and a strict read-result variant bind exact session/generation, selection revision, action epoch, dispatch/action/target, scope and observation revision. Parsing a valid contract does not activate a read. The normal one-second status exchange remains responsive while the separate owned Chrome job runs.

Initial support is top-level, active HTTPS documents only. Revalidate actual Chrome host permission and the exact tab/window/document/URL before injection, inject only the bundled fixed semantic extractor in ISOLATED world using exact tabId + documentIds (not frameIds together), require the returned documentId and frameId0, then revalidate identity and permission afterward. No arbitrary JavaScript, selector program, CSS, URL or file path comes from a model/page. No click/focus/navigation/form write/submit, background tab activation, screenshot, accessibility-wide desktop capture, cookie/storage read, or iframe traversal is part of this operation.

The extractor has a bounded node and time budget and never calls whole-document innerText/textContent before enforcing bounds. Its supported exclusion checks cover scripts/styles, hidden/inert/ARIA-hidden or collapsed regions, computed display/visibility/zero-opacity/content-visibility, unsupported clip-path/mask trees, forms/inputs/textareas/contenteditable regions and their descendants, password/autocomplete-secret surfaces, and unsupported trees. It reads only bounded rendered text nodes from the exact document; arbitrary page text remains untrusted evidence and cannot change grants, prompts or instructions. Page-controlled attributes/styles and layout are observations, not cryptographic secrecy guarantees or a complete renderer-equivalent visibility classifier. CSS clipping/overlap and inaccessible custom/shadow presentation remain unqualified; partial output never proves all visible content was read. No extracted content is logged or placed in general telemetry.

The bundled extractor visits at most2048 nodes, rejects depth beyond64, and admits no further DOM work after50ms of synchronous traversal. A single browser layout/API call is not preemptible; check the fixed budget again afterward and discard a late result. It takes bounded text-node prefixes before UTF-8 clipping and never materializes an unbounded DOM string or array. Shadow trees, frames and non-HTML document types are unsupported/excluded. Known replaced/media fallback subtrees (canvas, video, audio, meter and progress) are excluded entirely: their fallback text is not evidence of rendered content. One exact-request isolated guard retains only URL/request/revision/deadline and observer cleanup ownership; the read result remains outside that retained guard. The first DOM/input mutation retires the observer, and fixed expiry also cleans it. A metadata-only settled tombstone survives until exact finish acknowledgement, so an expired guard cannot be mistaken for a missing/unstarted read. A replacement never overwrites an unacknowledged guard.

Return at most16 ordered text blocks, at most512 UTF-8 bytes each and4096 bytes total, with bounded title/URL provenance (an empty title means not collected; the initial generic extractor uses URL/document provenance only). Traversal truncation and unsupported nodes are explicit. `message_limit` remains an upper bound, not proof of a mailbox's message count; the generic extractor never claims latest-N messages, account verification, full-page coverage or delivery confirmation. A generic page excerpt is always partial semantic evidence. Gmail latest-N/account/source/time verification requires its own qualified adapter and cannot be inferred from block order or a successful generic read. Unsupported requested semantics stay NeedsInput/Unsupported at the producer/driver boundary.

Native validation bounds the serialized result to the existing64KiB frame and enforces UTF-8 byte totals, strict enums, nonempty block content, exact original URL/document/scope/context, and explicit partial coverage. Empty/expired/changed/unavailable results carry no text. A successful read observation contains a bounded provenance/count/digest summary for durable dispatch history; raw page text stays transient in an opaque read-result owner for the accepted task. History must not reconstruct that owner or grant future page access. Any later retention into accepted memory needs its separate source/actor policy.

## Ledger schema 8 and the existing execution owner

Schema 8 adds one `browser_read_owner` row at singleton key 1. It contains an independent marker revision, the exact dispatch/action revision, strict bounded reading Context, and `pending` or `uncertain` state. Context contains identifiers and epochs only; no page URL, title, excerpt, credentials or DOM node is persisted in this slot. The dispatch and action revision reference existing immutable ledger rows and must agree with the decoded context and frozen dispatch source. The encoded context is bounded to 4096 UTF-8 bytes before serialization is stored and before recovery decoding. A missing row means no retained external browser owner; an invalid row means unavailable, never empty.

Before migration, reject any object using the new table name or attached to it in an older ledger. Do not adopt an unexpected table with CREATE IF NOT EXISTS. On schema 8, validate the exact table SQL, required uniqueness/foreign-key layout and indexes and reject attached triggers or unexpected indexes. Read back and validate the at-most-one bounded row before running startup recovery. Migration and recovery share the existing Store transaction; supported older schemas advance to 8 and newer schemas remain unsupported.

Any retained row blocks **every new effect claim**, including native app/volume actions, because they share the actual native input/effect owner. Enforce this in Store::claim_action itself, inside its claim transaction, not only in a browser adapter. Store::validate_dispatch likewise rejects authorization while the slot belongs to a different dispatch. Existing management, status and exact withdrawal remain possible on that same worker when it is not physically blocked. The active cancellation signal does not need the worker's SQL lock. No second Store or replacement worker may be opened to bypass the slot.

The specialized browser-read preparation is performed on the existing ExecutionController owner after a durable action claim. It resolves a complete immutable Request, validates exact permit correlation, and retains the original monotonic action/read deadline before any bridge publication. Its final authorize callback is called once: it revalidates the Store dispatch and original cancellation/deadline, persists the singleton marker on that same Store, then rechecks deadline/cancellation after storage returns. Only success permits one native publication. A marker left by a failed or uncertain storage commit blocks further effects until exact readback; an error never licenses publication. Ordinary adapters do not acquire this marker. ReadPage disclosure cannot call the generic authorization path without the specialized prepared request.

There are two retirement paths, both on that original ledger owner. Before any bridge publication, the same controller can prove its callback failed or its owned native queue never accepted the request; it may remove only its exact marker revision/context. After publication may have occurred, only an exact authenticated settlement for that marker can retire ownership. The native browser coordinator validates the actual installed connection/pairing and full original context before issuing a private, non-deserializable settlement capability to the worker. Raw frontend values, a parsed content Reply, a timeout, an ordinary success result or a caller-supplied boolean are not settlement capabilities. A callback must not open a Store or enqueue a marker mutation behind the worker currently waiting for it.

A live unresolved job retains the actual native worker until exact settlement, even when its ten-second content budget expires. Loss of the selected transport exposes uncertain ownership and withdraws content immediately. If that owner process ends, startup changes `pending` to `uncertain` while existing running-step recovery records UnknownEffect; it does not delete the row. Generic finish_observed_action, task cancellation and reconciliation do not delete or replace the external slot. Settling later may remove only resource ownership, without changing an already-recorded UnknownEffect/cancelled history or recreating a read handle. A fresh authenticated connection may deliver surviving old-context settlement only through a withdrawal-only recovery path tied to the same original pairing revision and exact marker; new session authority never revives old content. If the original receipt cannot be recovered, verified browser lifecycle termination is required and is currently unavailable; no user reset, reconnect, nonce or service-worker restart substitutes for it.

Implementation is staged: first schema validation/recovery, claim exclusion and read-only ownership status; then the specialized controller callback and native capability path; then v6 transport and actual extension settlement ownership. The schema-only stage exposes no marker writer or retirement command and cannot start a read. These are integration dependencies, not a completed semantic workflow. Tests and runtime browser operations remain excluded by the current user instruction; source review and static checks cover only the implemented boundaries.

| Entry point | Schema 8 decision |
| --- | --- |
| Store::open / migration / restart | Validate exact new schema and bounded row; retain uncertain external ownership |
| Store::claim_action | Reject every new effect while the singleton exists |
| Store::validate_dispatch | Reject a different retained dispatch; same dispatch still needs all ordinary policy checks |
| ExecutionController browser preparation/final authorization | Persist exact marker before one publication through the existing owner; forthcoming specialized path |
| Native browser result / settlement | Content and resource retirement remain distinct; forthcoming private authenticated settlement capability |
| finish_observed_action / task cancellation / reconciliation | No external-owner deletion, no replay or raw-read reconstruction |
| Store read-only ownership status | Bounded metadata only, no authority or reset handle |
| Settings / model / extension page messages | No direct Store, marker, arbitrary read or retirement command |

## Native receive and cross-crate capability boundary

A public serialized `browser::Authenticated` remains wire data and cannot construct settlement authority. The native receive prerequisite moves actual pipe receive/decode and contiguous envelope ownership into an opaque avesra-windows receive owner. Its constructor consumes the real browser_pipe::Connection and the original Admission, reads the first Hello from that connection, and returns the pending challenge plus its uniquely bound receive owner. There is no constructor from caller-provided Hello, bytes, session fields or a boolean for this authority path. The pending challenge retains the same private connection identity through issuance/storage work.

Every subsequent message comes from that owner's Connection::receive. It validates exact challenge session, positive contiguous sequence, monotonic observation revision and phase before exposing a typed message. A pre-authentication session accepts only polling, its exact Authenticate response or Disconnect; scope/document/read results require successful native authentication. The Authenticate message is wrapped in a non-Clone, non-Deserialize token bound to this actual receive owner. Consuming that token and original Pending verifies the saved credential/transcript and produces an opaque native authenticated seal plus the existing serializable wire response. Installing that seal on the same receive owner transitions its phase and retains the exact authenticated installation/connection/pairing provenance; a seal from another owner/challenge or past the original Admission deadline is rejected. The application still performs its current generation/selection/owner recheck under Runtime.local before publishing authentication. Native transport authentication does not grant scope, task, page or account authority.

The receive owner retains the last consumed sequence and observation revision across authentication and never exposes its underlying Connection for replacement. Send operations preserve the existing bounded framing/poison-on-cancel behavior. An invalid/malformed/out-of-order frame permanently poisons this owner, as does interrupted partial I/O. Decode/identity validation happens after actual receive, never through a public method accepting arbitrary caller bytes. Settings setup, issuance, current status semantics and v5 wire shape remain unchanged in this prerequisite; v6 read/settlement variants are added together only when integrated.

With v6, only this authenticated actual receive path may mint a private Windows settlement capability from a validated wire settlement. That capability contains the full original read context and receiving authenticated pairing provenance, but no excerpt or new action authority. The existing Windows effect worker consumes it together with its retained opaque core marker lease. A fresh connection may retire an old-context marker only under the documented same-original-pairing withdrawal path; its sequence is current while the settled read context remains frozen. There is no public constructor accepting Context/settled=true, and no frontend command exposes the native capability or receive owner. Core retirement validates its exact opaque marker and immutable dispatch binding; Windows supplies the separately proven transport provenance through possession of that capability. Ordinary serialized status/reply parsing cannot substitute for either half.

This prerequisite does not register a ReadPage route, add scripting permission, publish a marker, or issue a semantic job. Its purpose is to make the eventual constructor boundary real across avesra-core, avesra-windows and the desktop coordinator, before adding durable publication/settlement. Actual local-code/native-component compromise remains outside the same-user boundary; native Rust interfaces are not presented as protection against arbitrary code executing inside the companion process.

## Specialized worker and publication handoff

The next controller path retains a mutable borrow of its existing Store for the entire browser execution, from claim through preparation, marker publication, external settlement and ordinary dispatch finalization. It exposes the claimed permit and shrinking budget to the trusted native worker, not a new Store or webview command. Claiming the wrong action family must finalize the claimed dispatch as unsupported/failed rather than leave a running action orphaned. Generic EffectAdapter authorization rejects ReadPage disclosure; the native app/volume path and unsupported result behavior remain unchanged.

The existing NativeEffects worker creates one bounded native browser-work channel during runtime construction. Its receiver is taken exactly once by the desktop browser coordinator; there is no replacement receiver while old work is retained. Work items and completion handles have private fields, no Clone/Deserialize and no constructor from serialized Context. Only the original worker can create them for its current claimed permit. The coordinator's preparation reply is bounded native context data, not authority; the worker rechecks exact permit correlation and its own catalog/scope records before final authorization. It never queues those checks behind its own running command.

Final authorization is one attempted transition, including a failed attempt: validate original action/source/cancellation/time, invoke current native browser-context validation, create the exact singleton marker and read it back, then recheck original time/cancellation and native context after storage. Success yields two distinct non-clonable values: an opaque core marker lease retained by the actual worker and a native publication permit handed to the coordinator. The latter carries the immutable request and original deadline/cancellation, without Store access. An uncertainty during marker commit produces no publication permit and leaves readback/recovery required. The core marker lease cannot be reconstructed from UI/history, and no public retirement function accepts only a serialized Context or settled boolean.

The native publication permit has an atomic lifecycle shared with the original worker. Before any request can appear in a status frame, the receive owner takes that exact permit under current session/selection/action validation and irreversibly marks it possibly published. Serialization/send failure after that boundary stays possibly published. If a queue rejects the still-owned permit, or its owner drops it without ever making it visible, the worker may retire its exact core marker as provably unpublished. A caller timeout or cancellation while the permit is still queued is not proof of non-publication; retain ownership until the permit is returned/dropped or the coordinator reports actual settlement.

For possibly published work, only the opaque Windows settlement capability minted by authenticated ReceiveOwner may complete the channel. The Windows worker checks its exact context and original pairing against the retained publication/marker identity, consumes the capability, then consumes the core marker lease in the same Store owner's exact compare-and-delete transaction. The concrete cross-crate interface therefore passes an existing owned lease plus a privately minted native capability, not a new authority factory. Failed compare/readback leaves ownership blocked. Content result validation and publication additionally require all original live authority/deadline checks; settlement alone permits neither content nor a new action.

Completion of the browser-work channel means actual API/guard settlement, not the ten-second content timeout. The worker can expose display-only waiting/uncertain metadata separately, while its actual job and exclusive process/input owner remain held. A disconnected or dropped coordinator cannot release possibly published work; the retained core marker survives process exit. Recovery of a marker without its original in-memory lease requires the separately specified authenticated exact-settlement recovery path and is not supplied by a generic lease constructor. Both that recovery integration and verified browser termination remain closed until implemented.

## Lifecycle and actual job ownership

Use one extension-global actual Chrome job slot shared with metadata observation, including across connection replacement. Dispose/timeout immediately suppresses publication but retains the slot until every started API promise settles. No Promise.race releases actual ownership, and no fallback or queued automatic retry starts another read. Once Chrome has accepted an injection, native cancellation cannot prove it never executed; withdrawal prevents further admission/publication, while a delayed submitted job may still finish. Preserve unknown/disclosure history accordingly rather than claiming rollback. Keep at most64 read request identities per connection with no live eviction or UUID reuse; exhaustion requires explicit reconnect.

Content result and actual-job settlement are different facts. The integrated protocol must retain an exact request/dispatch/connection settlement receipt after every started Chrome promise and isolated-world guard cleanup settles, including canceled/expired jobs whose result contains no text. The receipt only releases resource ownership; it cannot revive expired content, authorize another read or turn UnknownEffect into observed success. Deliver it through authenticated contiguous status exchanges and retain it until native acknowledgement. No result or timeout is implicitly a settlement receipt. At most one unsettled read exists; do not queue replacements.

Native deadline/cancellation closes disclosure publication immediately but retains the actual effect owner until that exact settlement is validated. Disconnect or lost settlement leaves an explicit uncertain browser-job owner, not an available slot. Persist that uncertainty before publishing the request on the existing ledger owner so companion restart cannot silently free possible external Chrome work. Status/history may report uncertainty but may not reconstruct a read handle. A new nonce, selected transport, arbitrary user acknowledgement or fresh service-worker instance is not proof that an old Chrome injection finished. Recovery requires exact surviving settlement or separately verified browser lifecycle termination; that lifecycle proof is unavailable in the current runtime and no reset shortcut is enabled. Admission that provably never published a request may retire without external settlement, under the same actual native coordinator ownership.

Navigation, BFCache/lifecycle, history/fragment, relevant tab/window/user-context, permission removal and action-mode events synchronously invalidate observation before any awaited API. Semantic extraction additionally returns an observation-local DOM revision. Its bounded isolated-world guard must survive extraction through final document revalidation, drain pending MutationObserver records before final acceptance, and retire on result/expiry/disposal; an extractor that disconnects its observer before the final awaited API checks cannot attest that interval. The guard retains revision/identity only, no extracted text or page-node handles beyond its fixed operation lifetime. Mutation/user input during the read invalidates it rather than claiming an atomic page snapshot. Native acceptance still checks current remote observation revision and current local authority. A lifecycle event after a reply may revoke its freshness; it does not erase the immutable fact that an earlier bounded read occurred. Read observations expose no executable element handles. Later fill/submit must create fresh node-bound semantic handles with immediate pre-effect role/name/value/editability/draft rechecks; this slice cannot be reused as element authority.

Authenticated contiguous late results for canceled/expired requests are consumed and discarded without tearing down the selected transport or recreating authority. Malformed current replies and invalid session/sequence remain errors. Settings hide only withdraws management; an independently admitted accepted read uses its task/action lifetime. Mic mute/deafen and capture churn do not revoke accepted browser tasks. Stop/pause/lock/disconnect, exact task cancellation, actor/grant/scope/selection revocation do.
