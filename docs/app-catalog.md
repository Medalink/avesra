# Native application identities and launch outcomes

Application discovery is read-only. Implemented source paths select explicit local executables and read Start menu shell-link metadata and Windows App Paths registrations. Current-user packaged metadata discovery and protected immutable selection are implemented; packaged window observation, bounded focus and exact-AUMID activation source are implemented but unqualified. See [packaged application identities](packaged-apps.md). Discovery never follows a shortcut by launching it, invokes a shell, repairs MSI advertising, resolves a link with UI/network side effects, or treats a model string as an executable. A discovered item is a candidate, not accepted action authority.

An owner-selected identity receives a new immutable application UUID and revision. It preserves its executable or package identity, original arguments, working directory, source, display name, verified publisher when available and window hints. Executable identity includes a bounded SHA-256 digest, file length and native volume/file identity. Replacement, version drift or changed arguments requires a new identity; an old UUID can never be rebound. A persistent catalog rejects unsupported schema, malformed records and duplicate identity mutations. Revocation retains the historical identity. Aliases must resolve to exactly one current owner-selected identity before planning; ambiguous matches require selection before any launch.

`LaunchApp` accepts only an existing application UUID, bound to the action's target UUID. The single native effect worker reads the immutable catalog, validates fresh identity and rechecks its durable dispatch authorization immediately before the OS effect. Executable launch uses an explicit executable path and preserves its trusted native argument string, with no command interpreter or inherited standard streams. The executable remains open without write/delete sharing through launch to prevent replacement between validation and use. This does not attest every loaded DLL or mutable application data.

A returned process handle alone is not successful opening. The adapter correlates the launched PID, queried executable path and visible top-level window before returning success. Missing observation, process delegation, single-instance redirection, modal ambiguity or a failure after the commit boundary returns an unknown effect for explicit reconciliation, never an automatic retry. Observation has a fixed deadline; worker ownership remains held until native calls return. Existing-instance focus is restricted to one eligible observed window for an identity with empty arguments; packaged activation uses exact current-user registration and its separate typed identity observation.

Successful window observation additionally requires an explicitly native-configured expected class, no owner window, enabled/visible/uncloaked state, one matching window and a final process/window/PID recheck. A raw executable selection has no learned class and now returns NeedsInput before any launch. These checks establish the observed main-window identity at that instant, not application-specific readiness, completed login or absence of every custom in-app modal. Publisher remains unknown until a signature verifier supplies actual evidence; no display label is promoted to a verified publisher.

Source follows Microsoft's [CreateProcessW contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) and [shell-link metadata contract](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishelllinkw-getpath). No application discovery, launch, focus or window enumeration is invoked during the owner's gaming restriction. Runtime effects and UI onboarding remain unqualified.

Start menu scanning uses the two Windows Programs known folders, depth four, at most 2,048 examined entries, 256 returned candidates and five seconds of new-work admission. Reparse entries are skipped. Links are at most 2 MiB and are loaded read-only into IShellLink; only raw path, arguments and cwd are read, never Resolve. Empty/advertised, relative, environment-dependent, oversized or potentially truncated targets are rejected. COM and filesystem calls retain their actual lifetime; the admission budget does not falsely claim to cancel a blocked OS call.

App Paths scanning retains HKCU/HKLM and 32/64-bit origin independently, so duplicate names remain distinct choices. Only bounded REG_SZ executable metadata is accepted. A nonempty registered PATH addition is preserved but makes the candidate unsupported because direct executable launch does not yet reproduce that environment. No cwd is invented when registration omits it: native selection must provide one. This follows Microsoft's [App Paths registration contract](https://learn.microsoft.com/en-us/windows/win32/shell/app-registration). Both discovery paths report skipped/truncated results instead of claiming completeness.

Selection re-reads the native source and rejects changed candidate metadata before hashing the selected executable and issuing fresh immutable UUIDs. Source identity is retained with the catalog entry; older explicit entries without that optional provenance remain bound to their existing immutable executable identity. Visible native Settings can explicitly request discovery and choose a native-generated candidate ID; model strings cannot supply paths or source metadata. No catalog has been populated during this execution. Discovery, folder choice and launch remain uninvoked.

Protected setup uses native-generated discovery/candidate IDs with a fixed expiry and Settings/connection context. The UI chooses an existing candidate and an alias; it cannot submit executable arguments, actor identity, a catalog revision or an arbitrary model-provided path. Missing cwd is a required native folder choice before publication. Candidate revalidation and hashing happen off the UI thread; the one effect worker alone commits the immutable app and alias together, with fresh principal/proof authorization immediately before that write. An alias maps one normalized owner-selected phrase to one immutable app revision. Duplicate phrases require explicit resolution rather than silently replacing a target. Forgetting is revision-bound and does not revoke or undo a separately accepted task.

The native Settings commands and Learned names UI implement this setup workflow. Application observation toggles remain separate from launch aliases and grants. The approved Learned names card supplies its divided rows, fixed 120px phrase column, target/detail, unverified last-success indicator and size-7 Forget action. There is no simulated launch history. The inline selector displays the actual source, executable, arguments and cwd; absent cwd requires the explicit native folder picker. Windows verification is performed in the same section after reviewing the candidate, with durable owner creation remaining in People & Voice ID. No UI has been rendered or operated during this checkpoint.

Catalog schema 2 upgrades exact schema 1 transactionally without rebinding any app. Remember inserts a fresh app and alias in one transaction after duplicate/size checks, then rechecks native authorization immediately before commit. Forget checks alias UUID, revision and owner actor, deletes only that mapping, and rechecks immediately before commit. It leaves the immutable app, existing grants and accepted tasks intact. Both commands and bounded listing run on the existing effect worker; no second live Store is opened. Canonical phrases collapse whitespace/lowercase, are at most 64 characters/256 UTF-8 bytes, and accept letters, digits, spaces, apostrophes and hyphens.

The native folder picker uses an owner HWND and filesystem-only folder mode with no recent-item entry, following [IFileDialog options](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifiledialog-setoptions). It supplies only a native-selected local cwd. Its [modal Show](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-imodalwindow-show) may remain blocked until the user closes it; ownership must remain held, and stale/expired setup must reject its result. It has not been invoked. Picker selection alone neither publishes a catalog entry nor launches a program.

One native setup slot owns discovery/picker/queued catalog work through actual completion even when IPC disappears. Read-only discovery preserves at most 768 entries from three independently bounded sources; candidate IDs expire after 120 seconds and the Settings panel expires after 10 minutes without extension. Busy admission cannot clear another operation's candidates. Close, section disposal, lock and connection replacement invalidate panel ownership. A fresh one-use proof is consumed before any protected operation awaits, and final principal verification occurs outside local locks; proof and panel are then checked together under one local-state lock immediately before the catalog commit. A possibly committed result after context invalidation requires explicit status refresh, with no automatic retry or rollback. Forget affects only the mapping, not the immutable target or existing task/grant authority.

Both the custom title-bar hide and native close path invalidate native catalog/setup ownership before hiding and emit `settings-hidden`. The still-mounted Learned names component discards its async publication generation, panel and candidate IDs on that event. Its next explicit refresh opens a fresh panel. The frontend has no raw window-hide capability; all application hide controls use the native lifetime path. General setup-proof cancellation does not invalidate the catalog panel, because verification and conditional lock-banner cleanup occur within the mapping workflow.

The native planner resolver accepts an exact normalized phrase and current actor, returns one immutable alias/app revision, and rejects missing, foreign-owner, revoked or malformed mappings. It cannot perform fuzzy matching, choose among similar display names or create accepted intent. Planning must freeze the resolved app UUID into the proposed payload; later forgetting the alias cannot retarget that UUID. The resolver is available only through the existing native worker, with no webview/model authority ingress.

Catalog last-success metadata comes from a bounded validated Application observation joined to the exact dispatch, action revision, actor, target and original immutable successful finalization. Ledger schema 4 records that outcome atomically with observation/state finalization, separate from mutable task/step state and later reconciliation. Legacy observations have no finalization proof and are deliberately not backfilled; reconciling an unknown effect cannot manufacture native-observed success. The UI presents the recorded date in the local locale; it is historical wall-clock metadata, not latency, current process state or readiness. Missing/invalid dates remain unverified, never proof that the application was unused. This source has not read or created any live usage history.

Historical lookup starts from the `(target_id, actor_id, outcome)` finalization index and materializes at most the latest matching successful finalization by insertion order before joining its observation/action/binding. It does not scan unsuccessful history on the effects worker. If that latest successful finalization lacks a valid original observation, the status remains unverified rather than searching older data for a more favorable claim.

Explicit window observation is available inside the native candidate chooser before Remember. It hashes/revalidates that candidate, examines at most 1,024 top-level windows with a two-second new-call admission budget, and retains at most 32 native hint identities. Only a matching executable's bounded caption, class and PID reach the UI. The hint retains the exact executable identity, PID, process creation time and native HWND; a user-selected opaque hint ID cannot supply a class or handle. Process image paths are resolved through native process/file handles and compared with canonical path, volume/file identity and size, while the selected executable digest is checked and its read handle held during the observation. The target token SID and Windows session must match the companion. This identifies the reported native image file; it does not attest process memory or application account/project state.

Hints expire after 30 seconds. Remember revalidates the selected hint after fresh candidate identity selection and again at the queued commit boundary, followed by current owner/proof/panel validation. The class is attached only to the newly issued immutable AppRecord; old UUIDs are never edited or rebound. Incomplete enumeration is shown explicitly. No observation or choice focuses a window or launches an application.

Runtime executable opening first checks for eligible matching windows. This deliberately conservative unqualified adapter can require input when the same executable owns auxiliary windows. A matching-image window that is hidden, owned, disabled, cloaked or has an unexpected class is evidence requiring input, not absence that permits another launch. Multiple eligible windows, inaccessible matching identity, missing hint, minimized instance, or any running instance with nonempty saved arguments returns NeedsInput before an effect. This preserves profile/project/argument semantics instead of discarding them through focus. A bounded process snapshot (2,048 entries/two seconds, basename prefilter followed by exact native identity) also detects headless/starting instances before launching. Inability to rule out a matching candidate stays NeedsInput; unrelated inaccessible processes are not guessed to be targets. OS/process creation races remain possible and are not described as a global single-instance guarantee.

For the one eligible empty-argument instance, the held process handle, creation identity, class and ownership are rechecked before the dispatch commit. Exactly one [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) call is made. Since [foreground activation may be asynchronous](https://devblogs.microsoft.com/oldnewthing/20161118-00/?p=94745), the adapter observes for at most 500ms, checking liveness/window identity/minimized state and actual foreground every 20ms. No repeated focus, fake input or AttachThreadInput workaround occurs. A verified foreground result is recorded distinctly; denial, interference or expiry after the call remains UnknownEffect. Pre-effect NeedsInput is preserved by the execution coordinator without pretending an OS mutation happened. These source paths have not been invoked or qualified on the owner's desktop.

Visible Settings also implements [explicit executable selection](explicit-app-selection.md) through the same owned native coordinator. The picker freezes a separate file fingerprint without inventing cwd or arguments, then requires explicit folder choice. Final publication revalidates this fingerprint before the optional fresh window hint and original proof/panel authorization. No picker has been invoked.
