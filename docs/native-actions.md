# Native action adapters

Native effects execute only after the controller durably claims an exact action revision and the companion independently validates its accepted intent, actor grant, current session/epochs, target revision and required local approval. Model proposals and webview arguments cannot supply that authority. Adapters accept resolved native targets; they never infer a target from a display label, arbitrary shell command, URL scheme or executable argument string.

Volume targets bind a stable WASAPI output endpoint ID. The adapter reads current scalar volume and mute separately, validates percentages within 0–100, changes only the requested scalar, then reads back the same endpoint. It does not automatically unmute. A relative request must first resolve to an exact bounded absolute value that becomes part of the accepted action payload. Store the actual previous value for an explicit later restoration; never claim rollback merely because the setter returned successfully. Endpoint disappearance, failed readback or an observed external change produces an uncertain/failed observed outcome and does not trigger blind retries.

App targets are explicit owner-selected catalog records with immutable revision, canonical executable/package identity and bounded allowlisted arguments. Discovery is read-only. Launching must use the selected identity, preserve existing user work, and verify the resulting process/window rather than assume API success proves the intended app opened. Focus, project/account selection and visible text remain separate fresh preconditions for later input. Administrative prompts remain under the owner's control.

The Windows lock/session hook, pause/stop and disconnect must invalidate admission before a new OS effect. Once an effect has crossed its commit boundary, report its observed outcome or uncertainty; cancellation is not rollback. Background COM work must own its apartment lifetime, avoid UI/runtime mutexes during OS calls, and return bounded categorized results without secret-bearing window content.

Current boundary: the Windows volume adapter is implemented and statically compiled, including stable endpoint resolution, separate mute observation, pre-commit authorization callback and verified/uncertain readback. It has not been invoked, connected to accepted-intent ingress or qualified on a device. App effects remain specified only. Server action admission remains closed. The owner is gaming, so no audio controls, app launches, focus, UIA or browser operations may be exercised during implementation. Microsoft defines [endpoint scalar volume](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nf-endpointvolume-iaudioendpointvolume-setmastervolumelevelscalar) as an audio-tapered normalized control value, not a linear acoustic amplitude measurement.

The companion now owns one synchronous effect worker and its separate native-actions ledger. A process-wide admission lease and Windows exclusive owner-file handle are acquired before ledger open/recovery and retained by the actual worker until it exits. Dropping a reply receiver or timing out a caller cannot detach COM work or free its slot. Management changes enter the same bounded queue and immediately cancel the active pre-commit lease; consumed approvals can be revoked without making them reusable. Local epoch/mode/session changes invalidate that lease synchronously.

The coordinator claims a durable exact revision, rechecks its grant, accepted payload, consumed approval, cancellation and fixed monotonic lifetime immediately before commit, and records observed success or uncertainty without replay. Schema 3 stores bounded typed volume/mute before/after observations in the same transaction as the dispatch outcome, bound to dispatch, target and action revision; the native receipt preserves the same observation. A crash before this result transaction leaves an unknown effect and no invented restoration value. Read-before/read-after cannot identify every transient external change overwritten between reads.

This is source integration with dormant admission: startup uses an empty immutable target catalog, the authenticated accepted-intent producer is still absent, and owner/voice readiness remains closed. No action route or webview setter was enabled, and no native volume operation was invoked. Actual target setup, owner acceptance, restoration UI and device qualification remain required before usable actions. Locked desktop Clippy and formatting passed; no automated tests or live effects were run.
