# Packaged application identities

This contract extends the native application catalog with packaged applications. Package discovery, selection and activation are not yet implemented at this checkpoint. They must not fall back to shell commands, executable-name guesses, registry repair or another Windows user's registrations.

Discovery uses PackageManager's current-user registration view (empty SID), reads each package's full name, family and publisher ID, and enumerates that package's AppListEntry records. It admits at most 512 packages, 256 candidate applications and five seconds of new native work. Each package contributes at most 64 entries. Oversized or malformed identity/display strings, failed metadata reads and enumeration limits are explicit skipped/incomplete results. Asynchronous native metadata operations retain their actual ownership until completion; an elapsed admission budget is not evidence that a native operation was cancelled. Discovery reads metadata only: no LaunchAsync, activation, repair, elevation or package installation occurs.

The native candidate binds exact AUMID, package full name (including version), publisher ID and current principal. The AUMID family must equal the package family. Publisher ID is Windows package identity metadata, not an independently verified company/reputation claim. The UI receives only bounded display metadata and an opaque native candidate ID. Selection re-reads the same current-user package and app-list entry before creating a new immutable catalog UUID/revision. A version change requires explicit replacement; no catalog target may silently follow an updated package or another application in the family. A package has no invented working directory or executable arguments.

An opening request still contains only the immutable application UUID, equal to the action target. Native activation uses IApplicationActivationManager with the exact stored AUMID, empty arguments and no error UI. Full package/AUMID registration and current principal are revalidated before the final durable dispatch authorization; that authorization follows potentially blocking inspection and immediately precedes the single activation call. The effect worker owns the native operation even if its caller disappears. No retry follows a post-commit error.

Activation's returned PID is an observation candidate, not success. Success requires that same live process's current-user SID/session, exact GetApplicationUserModelId and GetPackageFullName, process creation identity, and one eligible visible/enabled/unowned/uncloaked window with an explicitly selected native class match the frozen target. Process delegation, ApplicationFrameHost indirection, inaccessible identity, ambiguous/modal windows, changed registration or missing observation remains unknown/needs input; no unrelated host window is promoted to the app. Focus must use the same exact native identity checks and one bounded foreground effect, without fake input or thread-attachment workarounds. Setup hints must be selected before immutable publication, never mutate an accepted target.

Entry points are the native catalog's explicit Scan/Observe/Remember workflow and the existing serialized effect worker. There is no new model/webview authority surface accepting package strings, HWNDs, SIDs or classes. Candidate discovery alone creates no grant, accepted intent or execution permission. Historical successful observation must use the same immutable original-finalization contract as executable applications. Runtime invocation, UI rendering and empirical qualification remain deferred during the owner's gaming restriction.

The pinned windows 0.62.2 bindings expose these APIs; their existence is not runtime proof.
