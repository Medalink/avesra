# Exact browser origin grants

This implements the scope-setup slice under browser-documents.md: transactional native metadata, selected-session proposals, extension popup permission flow and Settings recovery are source-wired. No origin grant, Chrome permission request or document operation has been activated. Runtime interaction remains deferred. Specs and code only; no test/fixture harness is introduced.

## Native record

Use a dedicated versioned SQLite scope store for mutable permission metadata, distinct from the pairing credential's DPAPI directory. Each record has a native-generated non-nil UUID/revision, durable owner actor, exact selected-pointer revision, pairing UUID/credential revision, immutable browser application UUID/revision, canonical origin, supported operation set and display creation time. Model/page/extension text cannot supply native record IDs or turn a record into an accepted task. No credential is stored in this database.

Canonical origin is ASCII `https://` plus a domain host using the standard HTTPS port, at most 512 bytes. Domain grammar is at most 253 bytes with nonempty dot-separated labels of 1–63 ASCII letters/digits/hyphens and no leading/trailing hyphen. Wildcards, empty labels, underscores and trailing DNS dots are unsupported, even if the URL parser would preserve them. Parse with the shared URL implementation, reject credentials, controls/whitespace, IP literals, path/query/fragment, explicit default-port spelling and noncanonical case/encoding. Require exact equality with the parsed origin serialization. Unicode names must be explicitly represented by their canonical ASCII form. A Chrome pattern is derived only as this exact origin plus `/*`; it is not parsed back as native authority. Native equality remains exact even if Chrome host permissions cover a wider set.

The initial operation set is explicit bounded reading and same-origin navigation. Fill/submit are separate future operations requiring their actual accepted-action/approval integration; no blanket browser-control bit is introduced. Store a sorted nonempty duplicate-free set of supported operations. Reading/navigation permission does not establish mailbox/account/project identity or a successful workflow.

Initialization rejects any occupied unversioned database, unknown/ambiguous schema marker or malformed required tables before schema mutation. Initialize the supported schema transactionally. Publish under an immediate transaction with a fixed bounded busy wait, enforce at most 32 saved records and reject duplicate owner/selection/origin rows instead of merging or widening them. New native revisions are insert-only; changing operations requires explicit old-revision revocation and a new proposal. Read validates row identity against its bounded serialized body. Revocation checks exact UUID/revision and owner, removes that one record and cannot erase a replacement. Failed/uncertain commit is reconciled by exact status; no automatic write retry.

Schema enumeration filters only the literal `sqlite_` internal prefix, so similarly spelled user objects cannot hide from occupied/exact-layout checks. Schema 1 requires the exact native-created table SQL, including affinities, length checks and uniqueness, plus the three actual unique indexes on id, revision and (actor, selection, origin). Merely finding familiar table/column names or a version marker is insufficient. Equivalent hand-edited schema text is not silently adopted as a supported database. Original authorization is checked after transactional writes and directly before commit initiation; cancellation during an already-started commit may leave a saved result and must be reconciled, never claimed rolled back.

## Two-sided proposal and ownership

Visible native Settings creates at most one pending proposal for its exact currently authenticated selected connection. Consume the original native owner-management proof before awaiting owner/database work. Generate proposal IDs natively and bind owner, selected reference, pairing, app/revision, native session/transport generation, action epoch, canonical origin and explicit operations. Its fixed 45-second monotonic deadline includes all queue/browser/user waits; current original proof must still be valid at durable publication. Keep native management lifetime separate from selected transport lifetime.

The extension receives and owns the exact proposal in its background service worker over the authenticated native port with current v5 status before exposing an enabled popup approval. The popup displays the origin and operations. Only its direct click handler may call `chrome.permissions.request` for the derived exact host pattern, without first awaiting a background roundtrip; background/native arrival cannot manufacture that gesture. Chrome closes popups on focus loss, and continuation survival is not guaranteed. Retain the original proposal in the background rather than relying on a surviving popup promise. A lost popup result is unknown; it cannot approve a replacement, trigger request retry or speculative rollback.

Register permission listeners synchronously at worker top level. `onAdded`/`onRemoved` carry permission sets, not native proposal identity, so treat them as hints to reconcile actual state with `permissions.contains` against the already-owned exact proposal **only after exact popup initiation intent**. The popup click sends fire-and-forget intent carrying its displayed proposal/session/context before calling request directly; it does not await that message. The background checks and records intent against the pre-established current proposal. An event racing ahead of intent cannot complete it; receiving the valid intent itself starts reconciliation. Pre-existing browser permission also requires current native owner approval plus this proposal's explicit popup intent. There is no generic native-only permission reuse action.

Popup completion or status/reopen may reconcile an already-initiated exact proposal, including permission that emitted no onAdded; they cannot initiate an unclicked replacement. After every await recheck original proposal/session/selection/action context, observation owner and monotonic deadline. A restarted worker has no pending native authority and cannot resurrect it from a browser permission. A late browser-only grant may remain and is reported accurately; no current native record is inferred from it. Native port lifetime support is not proof that a popup's callback survives.

The native decision handler independently rechecks its original pending proposal, current session/selection/epoch, original owner proof and exact permission-result correlation before queuing persistence. The permission result is extension-observed evidence, never an owner grant on its own. The actual blocking writer retains its admission slot through completion; publication validates native current context after any database wait immediately before commit. Do not hold Runtime.local across SQLite, browser APIs or thread waits. The saved grant is not a DOM capability or executable AcceptedIntent.

Settings close/release cancels pending scope management but preserves only an already authenticated selected transport. Stop/Pause/action-epoch change, lock, disconnect, selected change and credential revocation withdraw the pending scope and all derived document admission before any later asynchronous result. `permissions.onRemoved` withdraws extension ownership immediately; native revocation messages remain correlated to exact current grant/revision. Any persisted native record remaining after independent Chrome permission removal is unavailable until actual permission is re-established through explicit setup; it cannot silently authorize an API call.

## Recovery and entry points

Settings must list/clear valid native grant records independently of catalog discovery or extension availability. A corrupt scope database is unavailable and preserved; do not delete/reinitialize it automatically. No page content is needed for permission management. Display actual saved/Chrome-only/unavailable state without calling any of them a verified live page or account.

| Entry point | Required boundary |
| --- | --- |
| Shared canonical origin and operation parser | Reject ambiguous or broadened input before proposal construction |
| Scope SQLite open/read/publish/revoke | Exact supported schema, bounded records, original commit authorization and revision-bound recovery |
| Native Settings proposal/list/revoke | Visible native management lifetime, original owner proof, exact selected session |
| Authenticated extension proposal receipt | Strict typed correlation and current observation owner; no user gesture inferred |
| Popup permission button | Direct gesture, exact derived host pattern, one retained browser promise |
| Permission result / onRemoved | No stale proposal adoption, no implicit grant expansion, immediate withdrawal |
| Future document/effect ingress | Requires actual native grant plus current Chrome permission, document identity and accepted task; absent in this slice |

The native coordinator uses a separate one-operation scope slot so status polling never waits on SQLite or the connection-lifetime work slot. Pending management invalidates synchronously on every native management-generation change. A writer already admitted retains actual ownership until completion. Native Settings exposes exact-reference list/cancel/revoke independently of app discovery, while the extension reports Pending/Saving/Saved/Declined/Unavailable as setup outcomes, not live document capability. Browser protocol v5 requires nullable typed scope status and exact-session/sequence ScopeResult; handshake and comparison domain strings are versioned to 5, with no v4 fallback. Credential schema and pipe framing remain unchanged.

Popup state has a fixed monotonic proposal deadline that cannot extend on refresh and a 2.5-second status freshness bound, both checked synchronously at click. Invalid/failed status reads disable proposal controls. The worker coalesces permission events arriving during a contains read, without issuing another permission request. Decline is an explicit exact-proposal negative decision and never starts a contains reconciliation. Native revocation removes only its own metadata and closes transport; independent Chrome permission removal remains an explicit browser-extension-settings action. No speculative permission rollback is performed.

Source/static evidence establishes implementation only. No Chrome permissions or sites are exercised during implementation, and their absence must not be relabeled as qualified M5 behavior.

Primary API evidence: Chrome documents [automatic popup closure](https://developer.chrome.com/docs/extensions/develop/ui/add-popup), [gesture-gated request and permission events](https://developer.chrome.com/docs/extensions/reference/api/permissions), [top-level service-worker listeners](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/events), and [worker lifetime/Chrome-version behavior](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle). The ownership/reconciliation design above is a conservative inference from those guarantees; actual permission-prompt/popup closure behavior remains unverified.
