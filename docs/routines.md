# Scoped routines

## Explicit one-step task routines

An owner may save a verified task as a named candidate in Settings. The native
writer copies its exact supported application, volume or fixed-diagnostic payload
and target identity from the original successful action; the frontend supplies no
action payload. Invocation accepts only the whole request `run routine NAME`
(optionally prefixed by `Avesra `). This new accepted turn resolves the current
private routine revision and an independently current exact target permission.
It creates an ordinary new sealed task; no previous grant, approval, permit or
accepted handle is replayed. Missing, disabled or changed targets require input.
A successful observed invocation validates that exact saved revision. Correction
creates a new candidate revision; deletion removes retained revision content and
dependent event text. This explicit save path does not claim scoped demonstration
or structural-drift/window-relocation evidence.

Routines use the sourced private store in [memory.md](memory.md), governed by
Plan 001 C6. A demonstration is explicitly scoped to a selected app/window or
granted browser origin, has a visible active indicator and can be stopped. No
general keylogger or permanently saved screen recording is introduced. Lock,
pause, excluded/credential surfaces and stale target identity stop observation.
Coalesce unchanged observations and discard stale background work before delaying
accepted speech or action verification.

Each revision contains typed operations, bounded parameter definitions, current
app/site identities, semantic pre/postconditions, ordinary required permissions,
source references and validation history. Credential/MFA entry is a user step,
not a saved literal. Coordinates alone are not a reusable target. A selected
display, window title, learned alias or demonstration is not a permission grant.

States are candidate, validated, stale and disabled. Saving an observed sequence
creates a candidate only. A successful actual invocation with verified outcomes
can validate that exact revision; model confidence cannot. Changed app structure,
origin/account, version or grants requires reobservation or input. Keep corrections
and prior revision provenance; do not replace a working definition with a guess.

Invocation produces proposed ordinary steps under a new accepted task. Reuse
the current grants, exact approvals, target checks, DispatchPermit and actual
effect owner. A routine cannot append to a sealed intent or grant itself the
authority demonstrated by a previous run. Send/delete/publish remain separately
approved effects. Stop/caller loss and uncertain effects follow the existing
ledger reconciliation; never replay an uncertain step automatically after restart.

Real demonstration, restart, invocation, harmless window relocation, structural
drift, correction and deletion must be observed through the product before A15
passes. A hand-constructed routine or a manual agent action is not that evidence.
