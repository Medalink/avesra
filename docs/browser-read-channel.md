# Native accepted-read channel

This implements the ownership contract in [browser-reading.md](browser-reading.md). The target registry is immutable setup metadata. The next channel connects the already claimed native action to that registry and the existing authenticated receive owner; it introduces no webview read command, caller-built Request admission, reconstructed history handle, or qualified accepted producer. Source implementation remains uninvoked under the current no-tests/no-computer-use restriction.

## Concrete owners and admission

NativeEffects creates one bounded worker-to-desktop preparation channel when its actual worker is spawned. Its native receiver can be taken once by the desktop runtime. No replacement receiver, second ledger owner or detached worker is created on disconnect. Each preparation offer has private fields, is neither Clone nor Deserialize, and is constructed only by that worker after ExecutionController::begin_browser_read claims the exact Action and borrows the existing Store. The offer exposes a read-only copy of the actual DispatchPermit and its shrinking budget, together with one-use reply ownership. Those fields are metadata; possession of an offer cannot bypass the worker's final authorization.

The existing submit path still accepts a step and frozen DispatchSession, never page text, document fields or a wire Request. It selects the specialized path from the stored Action payload on the same worker. ReadPage cannot fall through generic EffectAdapter authorization. A preparation offer cannot exist before a successful durable claim. Failure to deliver or accept the one offer withdraws that original operation; it does not enqueue a replacement. The original ten-second Instant starts at claim and is capped by the Action expiry. Queue, native inspection, authorization, Chrome preparation and result processing all consume that budget.

The desktop's private consumer resolves Action.target_id as the immutable UUID in the current authenticated native target roster. Action has no target-revision field: resolve this UUID and freeze its actual stored revision, rather than accepting a caller-selected revision. Recheck the actor, strict ReadPage origin and message limit against the claimed Action. The target contributes its saved scope, selected pairing/app, exact document and observation/target/resource generations. No target lookup establishes a grant or registration, and no lookup can retarget an old UUID.

After the bounded target lookup and resource reservation below, preparation verifies the current native owner/principal, validated paired device/certificate and acknowledged PC session/action epoch, exact actor registration revision, selected browser connection and unrevoked saved Read scope. Metadata admission closes before these potentially blocking inspections begin. The source capture epoch remains frozen accepted provenance; current microphone settings do not replace it. The worker validates its existing AppCatalog and ledger grant/source directly, without a desktop callback queuing behind that worker. Any separately owned scope/owner/pairing inspection runs outside Runtime.local and is retained through actual completion. Its final freshness check still uses the original claim deadline. No successful closure or DTO alone is described as qualified admission: only the private runtime consumer supplies this adapter, and the worker checks the resulting metadata against its claimed permit.

## Resource reservation and target lifetime

Resolve and capture the target under Runtime.local → browser.inner before reserving the native resource word. A worker-created one-use reservation token atomically compares the exact previously clear resource generation and changes it to blocked with a fresh generation. This token is tied to this offer, cancellation and deadline, not an arbitrary generation supplied by a caller. The native consumer performs that compare-and-swap while its target context remains serialized. Failure retires the offer; it does not retry against a newer word.

The worker retains the reservation identity. The private prepared-target lease stores both the original target/resource identity and this operation's exact blocked generation. Its later checks tolerate only its own clear-to-blocked transition; they still require unchanged target, observation, connection, selection, scope and actor generations. It neither rewrites the target nor allows another stale record to resolve. All other target uses, new metadata admission and status.document remain blocked. Pending metadata is synchronously withdrawn. Existing Chrome metadata promises still retain the extension-global job slot until they actually settle, so accepted read preparation must fail unavailable rather than overlap them.

Reservation release is owned by the actual worker after all native preparation jobs return and either proven never-publication cleanup or authenticated settlement succeeds. Dropping an async waiter does not reopen it. Resource generation remains monotonic; after release old target records are stale and a new explicit target choice is required. A failed ownership refresh leaves it closed under the existing receipt/readback policy.

## Preparation response and one publication

The one-use preparation reply carries a bounded candidate Request assembled from the actual permit and resolved native target, an immutable registration binding, and a native current-context checker retaining the original prepared ownership. These are checked data until ReadExecution.authorize validates them against the claimed permit and existing Store. The native callback may inspect its captured native state but cannot open the ledger or submit management work to its waiting worker. Blocking inspection completes before the locked final checks; no Runtime mutex is held across disk, OS, channel or pipe I/O.

After exact worker-side catalog/grant/source checks, authorize is attempted once. It retains the original deadline, writes/readbacks the publication marker on that same borrowed Store, and returns MarkerLease plus PublicationPermit only on success. The worker retains MarkerLease. A separate one-entry publication handoff transfers the non-clonable PublicationPermit to the private desktop read coordinator. An error before that transfer cannot invent a permit; a dropped held permit proves returned publication only through its existing CAS state.

The desktop performs its final live target/reservation/actor/registration/action check, then consumes PublicationPermit immediately before the first status.read serialization. A failed send after this transition is possibly published. Subsequent polls read only the same PublishedRequest with a smaller remaining budget; they never obtain another permit. Read and document metadata are mutually exclusive. The request is retired synchronously on withdrawal, but the worker's possible-publication marker and resource reservation remain until actual settlement. No native proof depends on successful HTTP/pipe delivery or caller presence.

## Withdrawal and the active wait

The existing State.active cancellation must gain an exact read binding: actor, registration revision, grant, selected pairing/scope/target and frozen source. The desktop binds that immutable identity before authorization; a captured withdrawal generation closes the race where revocation happens before binding. Actor-registration revoke signals this exact active read synchronously before remote/SQL awaits. Existing revoke_reply_registration only handles replies and is insufficient for this path. Exact task cancellation, grant/scope/pairing/selection withdrawal, browser observation/connection loss and current action invalidation also close the same signal. Unrelated actors/tasks remain unaffected. Settings hide and capture-only changes do not withdraw an independently accepted read.

The actual worker enters a bounded-poll wait over its preparation/publication/content responses and the existing one-entry authenticated completion mailbox. It does not run arbitrary queued management/effect commands reentrantly. Necessary withdrawal uses the synchronous signal; queued durable mutations run after active work retires. Each iteration handles at most one completion and checks the original deadline and cancellation. An expired deadline withdraws content/publication, not actual Chrome ownership. Native blocking preparation retains its owner until its result settles even if the budget expires.

The active loop must handle both settlement for its own Context and unrelated historical duplicate acknowledgements using its same borrowed ReadExecution Store. Add a read-only exact receipt lookup on the borrowed owner; do not expose its Store, open a second Store or queue the lookup behind this loop. A valid unrelated historical receipt can be acknowledged without touching the active marker. A same-dispatch live-plus-retired inconsistency remains an error. An unrelated missing receipt cannot retire the active marker or clear its resource snapshot. The opaque received Settlement is compared to the live MarkerLease before consuming that lease for retirement. Recovery continues to use the distinct uncertain-row handle when there is no live ReadExecution.

Disconnect, failed content delivery or local caller loss cannot establish external settlement. Once possibly published, the native owner stays occupied while waiting for a surviving authenticated settlement. If transport/work ownership is irrecoverably lost, persist uncertainty and retain the closed resource state; a replacement worker/process still observes the durable marker. There is no timeout reset. Receipt publication requires exact durable readback and ownership refresh. The pipe loop retains receivers and polls them only between complete ReceiveOwner frames; it never abandons an in-flight receive to service the worker.

## Content and retirement are separate

Actual ReceiveOwner validates each contiguous content envelope and preserves its installed pairing provenance before the desktop routes one bounded reply to the matching active channel. No raw bytes, deserialized Context or caller-supplied settled boolean creates a native proof. Late authenticated results are consumed and discarded after withdrawal. The first exact result is retained at most once; an unrelated result cannot replace it. Malformed current content closes publication without freeing actual ownership.

Resource settlement may arrive before content and permits only receipt/marker retirement. Matching settlement stops further status.read publication immediately through a separate terminal-publication state. It does not cancel the original content authority: an already-sent matching result may still arrive and be validated within its original deadline. Neither repeated polls nor a duplicate acknowledgement may advertise or reinject that settled request. PublishedRequest's cancellation/deadline alone is insufficient for this distinction.

Receipt retirement/acknowledgement does not release the active operation's reservation. Keep the concrete worker and blocked reservation until content finalizes or is definitively withdrawn and every native preparation job has returned. Reopening early would invalidate the operation's own prepared generation and could overlap later work. The idle recovery handler's row-refresh policy is therefore not the active-loop release policy; an unrelated historical acknowledgement also cannot reopen this reservation, including before its marker is written.

Content finalization separately requires the original Request, current cancellation/deadline, exact current native context, actual permit and Store revalidation. A settled job with missing, expired or withdrawn content remains UnknownEffect as appropriate; settlement alone cannot manufacture Success. Typed durable provenance stores only bounded identity/count/digest metadata, while raw text can leave the worker only in a private transient reply owner for the accepted task. History never reconstructs it. A caller disappearing after durable finalization does not erase the historical result, but prevents transient reply publication.

The first channel prerequisite may compile its ownership types and retained worker plumbing with status.read still null and generic ReadPage still Unsupported. Enabling the specialized dispatch branch, publication, fixed extractor, scripting permission and extension settlement outbox is a separate coherent integration checkpoint: all required owners, synchronous withdrawal paths, content finalization and retirement must exist together. Neither intermediate source nor static checks claim a working browser workflow.

## Entry-point inventory

| Surface | Required treatment |
| --- | --- |
| NativeEffects::submit / Command::Execute | Stored payload selects specialized borrowed owner; no new raw Request API |
| ExecutionController / ReadExecution | Original durable claim, one authorize attempt, same-Store active receipt lookup and separate content finalization |
| NativeEffects spawn / desktop runtime | One take-once receiver, bounded one-use offers and publication handoff; actual preparation ownership retained |
| Native target resolver / resource word | Resolve UUID before own reservation; immutable revision and exact owned blocked generation afterward |
| Actor registration / grant / task / scope / selected transport controls | Synchronous exact active withdrawal, including pre-binding generation race |
| Browser status / actual ReceiveOwner | Current publication; contiguous authenticated result/settlement; no receive cancellation |
| Existing completion mailbox / restart recovery | Active-loop own settlement and unrelated duplicate lookup without second Store; uncertain recovery remains withdrawal-only |
| Extension Documents / future ReadJob / outbox | One actual Chrome slot across owners; no activation until final coherent integration |
| Settings document commands / ledger history | Metadata/display only; no accepted read entry point or reconstructed handle |

Validation under the user's override is source review, formatting, Clippy, type checking and bounded builds only. No tests, fixture harness, native/browser invocation or live page read is part of this work. The three required owner workflows and browser compatibility remain unqualified.
