# First authenticated owner and native management

## Automatic personal bootstrap (current product policy)

On a normal unlocked connected launch, a missing local owner may be created
natively for the actual current Windows SID without a Hello dialog. This is
create-only publication under the existing retained owner coordinator and current
session checks. Existing, unreadable, foreign-principal or revoked owner records
are never replaced. A missing paired owner registration may be established using
the same durable native registration intent and exact current actor identity;
uncertain operations are reconciled through actual status and never silently
transferred to another owner. Voice learning establishes only a provisional
speaker association with that Windows owner, never Windows identity or grants.
Advanced replacement, people management and protected actions retain verification.
This current personal-startup policy supersedes the historical manual-first setup
requirements below; those controls remain advanced management options.

## Guided owner setup

People & Voice ID presents three concrete setup steps: create the local owner, register that owner on the connected Spark, and save six voice phrases. Each step independently shows loading, completed, action needed or an actionable read error. Show only the first incomplete step's primary action. Registration is read automatically after owner/context changes and once a temporarily busy parent operation finishes; a capture/verification transition cannot leave an empty status with no retry scheduled. Failed reads require an explicit retry rather than a retry loop. Never infer registration from connection or mark unknown state complete.

The current build cannot activate automatic owner recognition. Say this prominently above the steps, distinguish this application limitation from a failed user setup step, and state that repeating saved enrollment or Windows verification cannot fix it. When owner/registration/recordings are confirmed, say that setup is saved and the app needs an update to listen automatically. The read-only voice check is optional troubleshooting, not a required activation step or proof of readiness. Replacement, selection, deletion, revocation, technical model IDs and comparison scores live in collapsed management/details sections. The main flow does not expose a separate unlock/countdown: each protected action already asks for Windows verification when needed. Page disposal still cancels native setup and any recording.

Entry points: EnrollmentView (coordinated setup/read recovery), ActorRegistration (same protected native register/revoke commands and automatic read-only status refresh), VoiceCheck (optional diagnostic only), SettingsView (page lifetime, prerequisite navigation) and SetupOverview (same activation limitation). Existing native identity/proof/permission gates are unchanged. Verification follows the owner's no-automated-tests instruction: Svelte checks, native compilation, builds, source review and real app bridge inspection.

All explicit protected People & Voice ID actions (create owner, begin enrollment, register/revoke on Spark, select/clear/delete a voice candidate) share the same frontend verification coordinator: inspect native proof, request Windows Hello if needed, recheck the mounted connection/owner context, then issue the named native operation once. Native one-use proof and exact publication checks remain authoritative. Verification's own capture-epoch transition must not discard its initiating UI continuation; actual owner, action, connection, lock, hidden-window or page-lifetime changes still cancel it. Refresh registration is read-only and never opens Hello. Registration reports progress and the resulting state inline and never navigates to Get started.

Settings remembers its last allowlisted section across reloads/restarts, separately from authentication or command state. A UI reload must not replay any protected operation. Stored candidate summaries refresh from native storage on People page mount and context changes; an obsolete request cannot erase a newer list. A saved six-segment candidate stays visible after native capture epochs change.

Candidate refreshes are serialized and coalesced: page mount, initial runtime, connection and capture-epoch changes cannot issue competing reads against the protected store lock. A refresh requested during an in-flight read runs afterward. Candidate loading/error state is independent of owner verification errors, retains the last readable list on refresh failure and provides an explicit retry. An empty list is only shown after a completed successful read; no pending/failed read is presented as absent enrollment.

A stored candidate that cannot be decoded is an existing saved voice with a read problem, not missing enrollment. Keep its identity visible, explain that the saved voice could not be read, and offer a retry without prompting for six replacement phrases. Only a successfully read, genuinely empty candidate list offers first-time recording. Entry points are native `list_candidates` / `speaker_candidates` and the guided and advanced views in EnrollmentView; selection, deletion, capture and qualification remain unchanged. Validate packaged production assets through the actual native bridge as well as development rendering; development-only evidence does not establish release behavior.

Refresh saved voice summaries when Settings regains focus and when Spark registration becomes confirmed, using the same coalesced reader as page mount and manual retry. Before starting first-time enrollment, re-read storage through that reader and stop if any saved voice is present or the read fails. This guard must precede Windows verification and recording. Only the explicit advanced replacement action may begin another collection when a saved voice exists. Keep Check saved voice available beside an empty-state recording action so recovery does not require finding advanced controls.

Saved voice lookup resolves the protected selected candidate's exact ID/revision directly, then enumerates additional records without duplicating that identity. A selected reference whose record cannot be read must remain visible with its bounded read error; it must never turn into an empty collection. A failed selection read with no readable candidate is a read error, not missing enrollment. All candidate decoding uses the existing native validated reader under the store lock; neither a reference nor a file name proves six completed phrases.

The `speaker_candidates` Settings response includes candidate summaries and the native storage directory (no vectors, protected bytes or audio). EnrollmentView validates this response's shape; an unexpected response is a visible error. Manual Check saved voice / Reload saved voices shows Checking immediately, disables concurrent clicks and reports the outcome and completion time even when nothing changed. A confirmed empty result names the checked directory and asks the user not to repeat prior recordings. The native command, selected-record lookup, initial/context/manual/pre-enrollment reads and both guided/advanced renderers are covered by source review and direct native observations under the owner's no-test-harness constraint; selection/writes/qualification are unaffected.

Storage diagnostics must report the resolved physical candidate directory, not just the logical AppData path. A parent MSIX package can redirect child-process reads and writes into its own LocalCache while reporting the normal path. Inspection evidence must prove the physical store matches an Explorer-launched release; an isolated desktop or absence of package identity alone is insufficient. Recovery of an original encrypted voice record/selection uses exact hash-verified create-only copies into the normal same-user store, with Avesra closed, preserving existing destinations and original files. Do not copy unrelated owner, credential, permission, ledger or settings databases, or mark recovered candidates qualified.

People & Voice ID guides explicit Create owner and Prepare enrollment actions through Windows verification when no current proof is available, instead of exposing a button that predictably fails for missing proof. A single button press authorizes verification followed by its named operation in the same still-mounted connected/unlocked UI context. Each native operation still consumes its own one-use proof; no frontend flag bypasses it. Creation and enrollment remain separate actions. After creation, explain the next step; enrollment reports missing owner, microphone, mute/deafen/pause and lock prerequisites beside its control. Successful read-only owner refresh clears stale owner errors. Page disposal or connection/lock changes must prevent delayed frontend continuation after verification. The agent must not authenticate as the user or record enrollment on the user's behalf.

The first explicit authenticated local setup creates one durable owner actor, bound to the current Windows process user's SID and protected with user-scoped DPAPI. The actor UUID is native-generated and stable across restarts. Windows principal, ownership and speaker identity are separate: owner creation never sets enrolled, voice_ready, speaker quality, accepted intent or action grants. An unqualified speaker candidate cannot become an actor simply by being selected.

Creation is a concrete Settings action after a fresh one-use Windows Hello management proof. An exclusive writer stages and syncs the encrypted database privately, then rechecks the proof's native challenge, Settings lifetime, connection generation and local epoch immediately before create-only hard-link publication. That publication is the ownership commit boundary. Closing/locking/disconnecting before it prevents creation and discards the private pending file. Cancellation after publication cannot undo ownership; the UI must reconcile stored status instead of retrying creation automatically. One coordinator retains work ownership through disk completion even if its IPC caller disappears.

The owner store rejects occupied unversioned databases, unsupported versions, ambiguous markers, malformed or foreign-principal records and failed DPAPI decryption. It never silently recreates or changes an existing actor. Readback returns only status and the stable native actor/revision, not SID or protected bytes. Other-user enrollment, grants, app selection and consequential approvals must obtain this same native owner identity and a fresh appropriately described management proof. Authenticated principal equality is checked again at use; a generic frontend owner flag is not authority.

Bootstrap and subsequent native management remain distinct from qualified voice activation. The Hello prompt accurately names people, ownership and permissions management. No Windows Hello invocation, owner creation, account inspection or permission change is performed during source implementation. Reset/recovery that would replace ownership requires a separate explicit revocation design; corrupt state remains closed rather than enabling a new owner.

Enrollment preparation reads the protected native owner and retains its actor UUID in the bounded enrollment session. Each recording and final candidate save rechecks that principal/actor without transferring an old command to a replacement session. Candidate selection/deletion additionally requires the same current native owner and fresh one-use proof. Saved speaker candidates still contain no owner permission or qualified profile: the collected-by actor is native management provenance, not a speaker identity verdict. The People card retains approved geometry and displays local ownership separately from unqualified voice setup; async owner replies are invalidated on lock, disconnect and section disposal.

Protected enrollment preparation and candidate selection/clear/deletion consume their exact proof synchronously before the first owner-read await. An older command cannot borrow a later verification. A profile change's own serialized invalidation may rebind that consumed proof to its new epoch without extending the original 60-second expiry or connection identity. Subsequent close, lock, disconnect or setup changes still revoke it. Native principal/actor and context are checked again immediately before selection publication or each deletion; cancellation between clearing a selection and deleting its candidate reports the partial result for explicit refresh, with no rollback or retry. Final enrollment saving similarly binds the completed session's context and owner through a fixed 30-second publication budget and rechecks after staging/sync immediately before the create-only publication. Pending blocking writers retain their owned context through completion even if the IPC caller disappears.
