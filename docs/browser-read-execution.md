# Completing the accepted-read owner

This is the next integration contract after [the native preparation channel](browser-read-channel.md). It completes the existing borrowed Store owner, publication handoff, authenticated content route and extension actual-job/outbox together. Until these pieces are coherent, the worker emits no offers, ReadPage remains Unsupported, status.read remains null and scripting/extraction stays inactive. The qualified accepted producer is still unavailable even after source integration; no frontend or setup command may supply an Action or page-read Request to bypass it.

## Claimed dispatch and original authority

The actual NativeEffects worker classifies the stored step using a bounded read-only payload lookup, then claims through exactly one controller path. Classification is routing metadata, never permission: begin_browser_read independently requires the actually claimed Action to be ReadPage, while generic execution continues to refuse ReadPage authorization. A changed/malformed/missing row cannot fall back to another effect. Frozen source session/capture/action provenance and accepted payload/grant checks remain in the claim transaction. No second claim, Store or worker is introduced.

The specialized path creates one offer from that ReadExecution and retains WorkerPreparation, the actual worker's native input slot and its original ten-second deadline. The runtime consumer performs the current native checks already implemented. The worker validates the exact configured AppRecord/revision on its own existing catalog, checks the returned Request against the actual permit and executes the retained native checker outside any Runtime lock. The worker does not reopen its ledger or queue inspection behind itself. It calls ReadExecution.authorize once, preserving the exact bounded prepared Request internally for subsequent content validation. A later caller cannot substitute a different document with the same Context.

The core owner keeps the full authorized request only transiently. Its durable singleton marker remains context-only. Failure before a publication permit exists uses existing never-issued cleanup; failure after handoff requires proof of returned or possible publication from the existing shared phase. No receiver/drop/timeout is treated as Chrome settlement.

## Publication mailbox and retirement

The runtime consumer's preparation response also returns a private one-use publication endpoint tied to that exact Admission and withdrawal record. It is constructed with the original offer and cannot be obtained from a Context or Request. The worker sends its non-clonable PublicationPermit through a bounded one-entry handoff and retains MarkerLease. The desktop coordinator stores the permit only if the original current target, registration binding, session/action, reservation generation and cancellation still match. It consumes it immediately before first status serialization. Status continues on the existing pipe loop; a worker wait never interrupts ReceiveOwner.receive.

The coordinator has distinct publication states: held, possibly-published, terminal. A matching actual settlement terminally stops status.read before acknowledging resource retirement. It does not cancel the original content authority. A result already sent before settlement can still arrive within the original deadline; terminal publication cannot be reversed by a poll, duplicate ack or delayed permit. Local withdrawal cancels content and publication together but retains resource ownership. Repeated status copies can only shrink PublishedRequest's remaining budget.

The native active loop services its bounded preparation/publication/content responses and the existing authenticated completion mailbox. It checks cancellation/deadline between operations and processes at most one completion per iteration. Native current checks retain the actual blocking owner and the same absolute deadline. Exact local revoke reaches the shared Cancellation immediately while a check is blocked. Remote registration changes are observed only through current checks; they are not represented as instantaneous local notification.

For its own settlement, compare the complete opaque received proof to MarkerLease, terminally withdraw publication and consume that concrete lease on ReadExecution. For another dispatch, use ReadExecution's bounded read-only retirement lookup on its still-borrowed Store. A proven historical duplicate receives its exact ack without touching the live request, reservation or marker. Missing/unrecognized metadata receives no ack. Same-dispatch live-plus-retired corruption remains an error. Never queue either path through the normal mailbox behind the worker that is waiting for it.

Retirement/ack can precede content finalization. The actual operation reservation remains blocked until content is finalized or definitely withdrawn and all native preparation/checker work has returned. The idle recovery handler's automatic row-refresh clear is not used inside this loop, including for historical duplicates before the new marker is written. Store readback failure withholds ack and cannot reopen a blocked owner. Releasing the exact worker token also requires the appropriate Store obligations to have completed; the token's preparation-finished flag alone is insufficient.

If a transport disappears or settlement cannot be proved, content is withdrawn and the durable marker becomes uncertain. The worker cannot admit another effect or metadata job. Existing authenticated recovery may later retire the exact surviving marker without recreating the read. No timeout, new browser session, fresh service worker, user reset or missing slot is a substitute for exact proof.

## Authenticated content and finalization

ReceiveOwner adds an opaque non-clonable content value produced only from an actual contiguous authenticated ReadResult frame. Its private construction checks the verified saved actor/app/pairing and the exact current browser session/generation. Unlike withdrawal-only settlement recovery, content cannot come from a replacement connection. The desktop compares it with the current pending operation and routes it through a one-entry result channel; no public raw Reply submission API is added. Late authenticated content is consumed and discarded without rebuilding authority or unnecessarily disconnecting the selected transport. Malformed current content remains an error.

The active core owner accepts content only for its retained authorized Request and actual DispatchPermit. It requires exact native context, original current cancellation/deadline, Store dispatch/grant/source revalidation and successful actual settlement before returning a content owner. Content is held at most once and bounded by the existing reply contract. It never runs model/page instructions, broadens scopes or changes the accepted task. A settled job without a valid current result finalizes conservatively as UnknownEffect; no history is rewritten by later settlement.

Add a discriminated BrowserRead observation to native effect history. Its encoded body is at most4096 UTF-8 bytes. It contains the immutable context, target/scope/document identity, partial coverage, block/byte counts, truncation/exclusion flags and a SHA-256 digest computed natively from the bounded canonical serialized Reply. Store a URL digest rather than the potentially2048-byte raw URL alongside the context. It contains no raw blocks/title, cookies, account data or executable handles. The observation validates exact ReadPage payload/target/action/source correlation and bounded fields before original native finalization. Empty and excerpt are distinguishable; generic evidence never claims mailbox message count or complete coverage.

Outcome mapping is fixed: before possible publication, proven never-issued/returned cleanup may record Failed, Cancelled, NeedsInput or Unsupported according to the original preparation failure. After possible publication, only a resource-settled phase plus independently current exact original content can record Success, and only for Excerpt or Empty. Unsupported, Changed, Expired and Unavailable replies, missing/malformed content, deadline expiry or withdrawal after possible publication record UnknownEffect with no transient text owner. A settlement alone never changes that classification. UnknownEffect preserves possible disclosure even when no content is accepted.

The finalization path atomically records its original typed outcome/observation through the existing ledger finalization transaction, then returns a private transient ReadReply containing the bounded untrusted evidence and its frozen provenance. It is neither Deserialize nor reconstructible from history and carries continued exact-source withdrawal for publication. Final cancellation/deadline/current checks run adjacent to commit initiation after blocking validation. Withdrawal observed by that final check prevents Success. Cancellation racing after the check may coexist with an actual commit; withhold transient delivery without rewriting history or pretending rollback. Keep cancel_requested monotonic and preserve the existing task-state rules, including explicit unresolved UnknownEffect rather than a new queued/successful task. Receipt delivery does not release the operation reservation before this finalization.

Successful handoff explicitly transfers the source signal/current checker into the transient reply owner before clearing active ownership. ReadExecution and WorkerPreparation currently cancel from Drop; their completed-success path must transfer or retain those concrete owners rather than immediately withdrawing every returned reply. Failed send/drop still withdraws. Reply consumption performs the retained current check once and yields only bounded untrusted evidence, never an effect permit; there is no public raw-body getter or history constructor. The exact task/actor/grant/scope/action withdrawal registration must remain continuous across this handoff, with bounded admission and no interval in which State.active has been cleared but its successor is not registered.

Ledger schema10 explicitly marks the new observation variant's compatibility boundary. It keeps schema9 table layouts and validates them before the version advance; it creates no content table and rewrites no historical outcome or observation. Existing app last-success queries continue to accept only their original application observation variants, never browser evidence. Older readers reject the newer ledger instead of silently treating a new observation shape as a known effect. Invalid existing required schema remains unavailable.

## Extension actual job and settlement outbox

The active extension read owner uses the same module-global acquireBrowserJob lease as Documents. It retains the lease through every actual Chrome promise and guard-cleanup promise, including after connection disposal, deadline or caller loss. It cannot release through a Promise.race timeout. A new request while actual ownership or an unacknowledged read outbox is occupied is rejected, never queued or substituted. Every request ID is retained in a bounded 64-entry per-connection seen set with no eviction or reuse; repeated identical status may reduce the original deadline but never reinject. An absent read withdraws content, not actual work or the metadata-only outbox.

Before admission and after every await, check the exact ObservationAuthority instance, current session/generation/action/selection, native observation revision, original deadline, requested scope/origin and real Chrome host permission. Revalidate exact tab/window/top-frame/document/URL through the documented APIs, including active lifecycle, non-incognito and usable tab state. Inject only the bundled self-contained beginPageExcerpt through ISOLATED world and exact documentIds; require exactly one matching documentId/frameId0 result and strict bounded result shape. No model-selected script/selector/URL or page-facing command is introduced.

Once injection may have started, keep actual ownership until the exact finishPageExcerpt call returns its matching metadata-only settlement and all API promises have settled. Revalidate permission/document identity before finish and require unchanged matching DOM revision for accepted content. On withdrawal, attempt only the same exact-document cleanup without re-enabling content; inability to access/verify cleanup retains uncertainty. An explicit correlated started:false return with no guard installed proves this request did not create one; a rejected/lost injection promise is not equivalent. Missing/unknown finish is not successful cleanup. Navigation or worker restart cannot manufacture a receipt.

An exact completed job retains one metadata-only Settlement outbox entry, independent of the disposed connection owner. It never retains text for reconnect. On the same valid connection send at most one content result, then settlement, using contiguous envelopes; their ordering is an optimization, not a native assumption. After reconnect only settlement may be replayed, bound to the actually authenticated same pairing. Clear the outbox solely on a full exact-context native read_ack, which represents durable native receipt readback. Unrelated/stale ack never frees it. Module/service-worker loss may lose that outbox, but native durable uncertainty still blocks accepted and metadata reads; no inference from a fresh module-global slot is allowed.

Background status handling remains responsive while the actual job runs: it does not await extraction inside the serialized control-message handler. All navigation/tab/permission/action events invalidate observation and current content synchronously before awaited inspection. Add scripting permission/import/dispatch only in the final coherent integration checkpoint, alongside this owner/outbox, never as a temporary arbitrary-page inspection route.
