# Selected browser profile and document control

M5 uses the user's explicitly chosen Chrome/Brave extension installation. The existing native messaging endpoint is status-only. Origin argv validation remains a routing check, not authenticated browser/profile authority. No browser API, page content, native-host connection or pairing is exercised during implementation.

The extension owns one native port and a fresh connection generation. Every message/disconnect callback captures that exact port and generation; stale callbacks cannot clear, publish for, or disconnect a replacement connection. Explicit disconnect invalidates ownership before closing the old port. Browser/extension restart invalidates all connection/document/element capabilities. Unrecognized or oversized native responses close only their own current port; they cannot grant readiness. Popup requests must originate from this extension's exact popup URL, have an exact schema, and cannot forward arbitrary page messages.

The next authenticated bridge is a versioned bounded Windows named pipe, with explicit current-user/session security descriptor, remote-client rejection, first-instance ownership and one owned request slot. Peer PID/principal/session and configured native binary identity are checked; origin strings and process names alone are not authenticators. Native messaging has its own strict length-prefix cap before allocation, UTF-8/typed schema limits and deadlines. No stdout logs or credential-bearing diagnostics are permitted.

The local transport layer is now implemented as dormant source in `browser_pipe`: a per-user/session v1 pipe name, protected DACL allowing the current token's unique logon SID, no inherited handles, first-instance/max-one-instance ownership, remote-client rejection, and client SECURITY_IDENTIFICATION. Kernel-reported peer PID/session must match the current native user/session and exact sibling installation executable's canonical file identity/hash. The retained process handle pins PID identity and must remain live. This checks the reported image file, not running process memory or the integrity of arbitrary same-user local code. Install replacement requires a new connection; no model/frontend path configures the peer executable.

Listener creation/connection is not wired to startup or native-host stdin yet; the existing native host remains status-only. The transport accepts a connection within 15 seconds, then owns peer inspection to actual completion off the async/UI thread. A duplicated pipe handle keeps that inspection safe if its waiter disappears. Each complete little-endian length-prefixed UTF-8 frame is 1–65,536 bytes with one five-second prefix/body budget. Oversize is rejected before allocation. Send/receive poison their connection before their first await and clear it only after full successful I/O plus peer liveness; an outer cancellation or partial frame cannot resume as a new frame. Owned mutable access prevents overlapping requests. Higher layers must still validate typed messages, credentials, generations and permissions: a transport connection is not a paired browser session.

The selected extension installation pairs through explicit native owner confirmation and a fresh one-use challenge, with a persisted credential bound to that pairing and native session/generation. Replays/restarts/cancellation invalidate challenge authority. An extension-generated installation UUID identifies a paired storage context; it does not prove a filesystem profile path or browser account. Any chrome.storage.local credentials require TRUSTED_CONTEXTS access, excluding content scripts. Page scripts never receive credentials, native port access or a generic message-forwarding route. Same-user arbitrary local code can compromise that user's browser/native processes; this bridge does not claim isolation from such code.

Pairing implementation must preserve this transaction order: explicit extension Connect supplies its installation/connection IDs and fresh nonce; native admission generates a separate session/challenge/nonce and displays the exact pending installation plus comparison code in visible native Settings. Authenticated owner confirmation consumes the original one-use setup proof and pending challenge before any await. The native owner/connection/challenge is rechecked immediately before create-only DPAPI credential publication. Only the same owned connection receives the credential, and the extension must set trusted-context storage access before persistence. An acknowledgment lost after native publication yields an unconfirmed pairing requiring status/revocation, never automatic replacement or repeated credential issuance. The UI label is owner-selected metadata, not discovered browser account evidence.

Reconnection proves possession with HMAC-SHA256 over a versioned, unambiguous challenge transcript containing the immutable pairing/installation identity, both connection/session identities and both fresh nonces. The credential is never carried in ordinary document commands or rendered/logged. Credentials have exact revision-bound native removal/revocation; either revocation or connection generation change invalidates pending commands and document handles. The admission clock spans peer inspection and challenge negotiation; blocking native work retains actual ownership but a late result cannot establish a fresh session. No authenticated command is admitted until both native pairing state and exact current transport session have been established. Native storage and a consuming handshake state machine are now implemented; an explicit native Settings coordinator is now implemented, while its UI and native-host/extension relay integration remain required for a usable paired connection.

The initial typed handshake uses browser bridge protocol 2, independent of the v1 pipe framing/name and existing status-only native endpoint. UUID strings are canonical lowercase/non-nil, nonces and HMAC are exactly 32 bytes represented by 64 lowercase hex characters, and extension IDs are exactly 32 characters a–p. The HMAC transcript is UTF-8 `AVESRA-BROWSER-AUTH-2` followed by LF-separated pairing UUID, credential revision UUID, installation UUID, extension connection UUID, native session UUID, client nonce, server nonce and extension ID, with a final LF. The fixed alphabets cannot inject separators. Verification uses a cryptographic constant-time MAC verifier, never ordinary string equality. A 45-second fixed monotonic handshake budget begins before peer inspection and is checked again before accepting authentication/publication; no message extends it.

Native stored pairing schema 1 must bind exact pairing/revision, owner actor, native Windows principal, selected browser catalog UUID/revision, extension ID, installation UUID, owner-selected display label, creation metadata and 32-byte credential. DPAPI is per user; the decrypted record is validated before use. The roster is bounded at 16 records with create-only staged durable publication. A corrupt or foreign record is unavailable, not automatically replaced. Exact filename/revision recovery must remain available without exposing decrypted credentials. Browser account, filesystem profile directory and runtime content permissions are not inferred from any saved label. Durable pairing is distinct from a currently authenticated connection and from action grants.

The saved browser catalog identity is owner configuration until independently correlated with the running browser. The extension origin, installation UUID and matching sibling native-host executable do not prove Chrome versus Brave, a filesystem profile path or browser account. Future launch/targeting must revalidate that exact immutable AppRecord and its actual connection; no speculative parent-process inference supplies that proof.

`browser_pairing::Store` retains a cross-process exclusive file lock through bounded off-thread storage work. Individual records are capped at 16 KiB, enumerated under a 256-entry directory budget and a 16-record roster cap. Temporary files never count as pairings; unexpected directory entries fail closed, while direct exact-revision removal does not require successful roster decoding. An opened final record handle rejects reparse points; this does not claim that all ancestor junctions are absent. DPAPI plaintext and owned credential buffers are cleared on drop. Status exposes only validated binding metadata or an unavailable summary with the filename's exact identity. A corrupt/foreign record blocks new issuance until explicit recovery rather than allowing a duplicate installation credential.

Publication stages and syncs encrypted bytes, then runs the original authorization callback immediately before a create-only hard link. Readback failure or expiry after publication is an uncertain saved result; refresh/revoke instead of retrying. `Pending::approve` generates immutable pairing/revision IDs natively and produces a consumed `Issuance` only for that original pending connection. Loading a saved record exposes no credential accessor and cannot construct another issuance. The issuance frame repeats the exact native challenge with the new pairing reference; the extension persists it before proving the same canonical transcript. A saved record alone remains unconfirmed with respect to a live browser; only the live coordinator's successful proof and current ownership can publish an authenticated connection. The six-digit comparison code is an explicit human comparison aid derived from the canonical comparison transcript, not an authenticator.

`Admission` begins before peer inspection, and `Pending` consumes itself on approval or MAC verification, including failure. Its generation argument is a snapshot, not synchronization: the coordinator must retain exact live session/generation/revocation ownership while accepting or publishing the result, re-read the durable pairing on reconnect, and invalidate the live session before revision-bound removal. No action grant is produced by these helpers. Status-only native messaging remains unchanged until that coordinator is wired.

After authenticated pairing, explicit native scope configuration authorizes supported HTTPS origins and operations. Host permissions are requested explicitly, not assumed by discovery. Native-owned target references bind pairing, connection/session, browser tab/window/frame, extension documentId, active lifecycle, independent observation generation and target origin. frameId alone survives navigation and is insufficient. BFCache/prerender transitions invalidate observations even where documentId survives; DOMContentLoaded alone cannot establish freshness. Tab closure, navigation, browser/extension restart, lock, permission removal, connection replacement and expiry revoke old references.

The canonical comparison transcript is UTF-8 `AVESRA-BROWSER-COMPARE-2` plus LF-separated installation UUID, extension connection UUID, native session UUID, challenge UUID and native nonce, with a final LF. Its SHA-256 first four bytes interpreted as an unsigned big-endian integer modulo 1,000,000 produce six zero-padded decimal digits. Pairing is excluded because the comparison precedes native credential creation; the HMAC independently binds the newly issued exact pairing/revision. JavaScript object serialization order is irrelevant.

The native `browser` coordinator now exposes explicit Settings start/status/approve/cancel and saved-record list/revoke commands. Start resolves one existing owner-selected learned application on the existing catalog worker; it never accepts an executable path from the webview. The bounded configured extension origin is loaded beside the native executable. A listener is created only for this explicit attempt, not app startup. The single owned work slot lasts through peer inspection and any actual storage job even after cancellation. Settings hide/close, lock, disconnect and explicit cancellation invalidate the attempt; native lock order is local state then browser state, with no window dispatch or disk/owner reads under those locks. Visibility admission snapshots generation before the synchronous window query so a concurrent hide cannot authorize a fresh attempt.

The initial relay surface is typed Hello, Authenticate, sequential Poll and Disconnect only. Poll binds the exact native session and contiguous sequence, starting at one. Pending owner confirmation is polled while a separately owned blocking writer runs; it does not extend five-second framed-I/O or the fixed 45-second handshake budget. Current attempt and absolute deadline are rechecked after receive and before publication. Approval consumes the original native proof and exact challenge before asynchronous owner reads. The final storage callback checks that same proof, owner-selected immutable catalog identity and pending challenge together under native synchronization. A completed issuance can be transferred only to its original owned pipe. Successful HMAC verification is committed under the same state lock; status becomes `authenticated_no_scopes`, which authorizes no page reads or effects. This initial explicit Settings session expires five minutes from attempt admission and requires ongoing polling; it is not a background reconnection service.

Saved-record status does not claim extension persistence or a current connection. Revocation first invalidates native connection ownership and then requires a fresh consumed owner-management proof for exact-revision disk removal. If an old native job is still running, removal returns a closing/busy outcome instead of opening another store; explicit refresh/retry is required. A failed or interrupted durable result remains uncertain, with no automatic credential replacement. These commands are source-wired but no listener, pairing, owner proof or stored credential has been exercised; the current packaged extension/native host still uses its legacy status-only route until the next relay slice.

Content-script semantic snapshots remain untrusted page data. Only bounded native-requested snapshots from the exact active document/frame may return at most 128 bounded nodes and fresh opaque element handles. Hidden/password/sensitive fields are excluded; selected account/project context must be separately established before input. No arbitrary JavaScript evaluation, CDP, cookie access, network interception, remote debugging port or caller-supplied DOM selector is exposed. A model proposal cannot turn a snapshot or page instruction into a grant.

Effects require an accepted exact action and the single native effect lease. Before input, recheck paired session, origin, document/lifecycle/observation revision, expected element and current user context. Filling preserves unrelated existing content; submission requires explicit accepted submit scope, one dispatch identity and observed postcondition. User navigation/focus/intervention or unknown outcome requires reobservation/reconciliation, never blind mutation replay. Login/MFA/CAPTCHA remains user input. All such effect admission remains closed until the authenticated pairing/controller path is implemented.
